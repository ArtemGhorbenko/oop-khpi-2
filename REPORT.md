# Звіт до лабораторної роботи №14

## 1. Варіант: 3.

## 2. Предметна модель
Було створено класи предметної області: `Product` (товар), `Order` (замовлення) та `Invoice` (накладна). Бізнес-логіку обчислення вартості та генерації накладних винесено в окремий детермінований клас `StoreService` для забезпечення можливості модульного тестування без залежності від планувальника потоків.

## 3. Реалізація багатопотоковості
Програма демонструє створення потоків двома способами:
1. **Наслідування `Thread`:** Клас `ProductVerificationThread` імітує фонову перевірку опису товарів у каталозі.
2. **Реалізація `Runnable`:** Клас `OrderProcessingTask` інкапсулює завдання з обробки замовлень та формування накладних. Цей об'єкт передається в конструктор класу `Thread`.

Обидва потоки запускаються в класі `Main` паралельно за допомогою методу `start()`. Імітація тривалих операцій (звернення до БД) реалізована за допомогою методу `Thread.sleep()`. Для синхронізації головного потоку з робочими використовується метод `join()`, який гарантує, що підсумкові результати в консоль будуть виведені лише після повного завершення всіх паралельних завдань.

## 4. Висновок
Під час виконання лабораторної роботи було успішно реалізовано паралельне виконання незалежних завдань в Java. Продемонстровано розуміння різниці між викликом `run()` (виконання в поточному потоці) та `start()` (створення нового потоку). Модульними тестами перевірено детерміновану бізнес-логіку сервісу, що є правильною практикою при розробці багатопотокових додатків. Порядок повідомлень у консолі змінювався від запуску до запуску, що підтверджує недетерміновану природу планувальника потоків ОС.
