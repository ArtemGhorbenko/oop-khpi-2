# Звіт до лабораторної роботи №11

## Варіант 3.

## Предметна модель та архітектура
Модель складається з класів `Task` (завдання) та `Developer` (розробник). Для управління процесом розроблено сервіс `Sprint`, який інкапсулює роботу зі стандартними колекціями Java (Collections Framework). Для коректної роботи з колекціями на основі хешування у класах сутностей перевизначено методи `equals()` та `hashCode()` за унікальними ідентифікаторами.

## Обґрунтування вибору колекцій
У сервісі `Sprint` використано три різні колекції, кожна з яких виконує специфічну роль:
1. **`Set<Developer> team` (реалізація `HashSet`)**: Використовується для зберігання команди розробників. Множина гарантує унікальність елементів, що унеможливлює випадкове додавання одного розробника двічі.
2. **`Queue<Task> backlog` (реалізація `LinkedList`)**: Використовується як черга завдань, що очікують на виконання. Забезпечує обробку завдань за принципом FIFO (першим прийшов — першим оброблений) за допомогою методів `offer()` та `poll()`.
3. **`List<Task> activeTasks` (реалізація `ArrayList`)**: Використовується для зберігання активних завдань. Список дозволяє швидко додавати елементи та зручно видаляти їх через ітератор під час пошуку за ідентифікатором.

## Висновок
Під час виконання лабораторної роботи було практично застосовано Collections Framework. Вибір структур даних `Set`, `Queue` та `List` було здійснено на основі вимог до бізнес-логіки планувальника завдань. Продемонстровано повну інкапсуляцію колекцій всередині сервісу та забезпечення типобезпеки за допомогою Generics.
