## Обґрунтування абстрактного класу
Базовий тип `Assessment` є семантично обґрунтованим, оскільки будь-яка форма перевірки знань (іспит, тест, проєкт) має назву дисципліни, максимальний бал та статус завершення. Проте саме поняття "оцінювання" є занадто широким для створення прямого екземпляра — неможливо оцінити студента, не знаючи формату роботи. Тому клас є абстрактним.
## Спільний стан і поведінка
- **Fields moved to the base class:** `title`, `maxScore`, `completed`.
- **Concrete methods in the base class:** `summary()`, `markAsCompleted()`.
- **Abstract method of the common contract:** `evaluate(int pointsScored)` — кожен тип оцінювання має власну шкалу, правила розрахунку прохідного балу та текстовий зворотний зв'язок.
## Спеціалізація підкласу
- **`Exam`:** Додає ім'я екзаменатора. Логіка `evaluate` перевіряє прохідний поріг (60%).
- **`QuizAssessment`:** Додає кількість питань. Логіка `evaluate` розраховує відсоток успішності.
- **`CourseProject`:** Додає прапорець необхідності презентації. Логіка `evaluate` формує вердикт щодо формату захисту.
## Поліморфний клієнтський код
Поліморфізм продемонстровано у класі `Main.java` та `AssessmentPolymorphismTest.java`. Створюється масив посилань типу `Assessment[]`, який заповнюється об'єктами `Exam`, `QuizAssessment` та `CourseProject`. Далі у циклі `for (Assessment a : assessments)` викликається метод `a.evaluate(85)`. Програма динамічно під час виконання визначає фактичний тип об'єкта та викликає його власну реалізацію методу.
### Додаткове завдання
- **Where the base-type call is demonstrated:** У попередніх моделях (наприклад, система готелю з ЛР2) можна ввести абстракцію. Класи `StandardRoom` та `SuiteRoom` є кандидатами на узагальнення.
- **Short conclusion about a possible abstraction in the earlier model:** Можна створити абстрактний клас `HotelRoom` зі спільним станом `roomNumber`, `pricePerNight` та `isBooked`. Абстрактним методом може стати `calculateTotalCost(int days)`, де звичайний номер просто множить ціну на дні, а `SuiteRoom` може включати фіксовану надбавку за міні-бар або обслуговування. Це дозволить менеджеру готелю рахувати прибуток у єдиному циклі через масив `HotelRoom[]`.
## Остаточний висновок
- **What the model demonstrates about polymorphism:** Модель доводить, що використання абстрактних класів дозволяє винести спільну логіку та стан на вищий рівень ієрархії, усуваючи дублювання коду. Клієнтський код стає відкритим до розширення (Open-Closed Principle): якщо завтра знадобиться додати новий тип `LabWork`, клас `Main` змінювати не доведеться, він автоматично зможе обробити новий тип через посилання базового класу.
